# Zoom Navigator Foundation + Authentication Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the secure Supabase foundation for username/password login, invite activation, JA creator identity, login lockout, forced password change, and one-session-per-user enforcement.

**Architecture:** Supabase Auth remains the password/session authority. Each app user has a hidden internal email stored only in a private table, while the public product identity is username + initials. Public login/activation Edge Functions use the publishable-key auth mode plus server-side secret-key access; protected admin functions use user JWT validation plus explicit JA checks.

**Tech Stack:** Supabase Postgres 17, Auth, Edge Functions TypeScript/Deno, `@supabase/server`, `@supabase/supabase-js@2`, pgcrypto/citext.

**Spec:** `docs/superpowers/specs/2026-09-17-zoom-navigator-team-access-design.md`

## Global Constraints

Use all constraints in the master plan. This plan must not modify the Medify project or any Medify tables/functions.

### Core tables

- `public.zoom_profiles` — user-facing identity/status only.
- `public.zoom_agent_slots` — JA-created pending/claimed initials slots.
- `private.zoom_auth_identities` — hidden synthetic email mapping.
- `private.zoom_login_security` — lockout counters + active `session_id`.
- `private.zoom_invites` — hashed invite codes and claim state.
- `private.zoom_admin_events` — append-only security/admin audit entries.

**Files:**

**Interfaces:**

- [ ] **Step 1: Write the migration SQL with validation constraints**

Use this shape:

```sql
create extension if not exists citext;
create extension if not exists pgcrypto;
create schema if not exists private;

create table public.zoom_profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  username citext not null unique,
  initials text not null unique,
  role text not null check (role in ('creator_admin','agent')),
  status text not null default 'active' check (status in ('active','deactivated')),
  must_change_password boolean not null default false,
  avatar_id text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint zoom_username_format check (username::text ~ '^[A-Za-z0-9_]{3,}$'),
  constraint zoom_initials_format check (initials ~ '^[A-Z]{2,3}$')
);

create table public.zoom_agent_slots (
  id uuid primary key default gen_random_uuid(),
  initials text not null unique check (initials ~ '^[A-Z]{2,3}$'),
  status text not null default 'pending' check (status in ('pending','claimed','disabled')),
  claimed_by uuid references public.zoom_profiles(id) on delete set null,
  created_by uuid,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table private.zoom_auth_identities (
  user_id uuid primary key references auth.users(id) on delete cascade,
  internal_email citext not null unique,
  created_at timestamptz not null default now()
);

create table private.zoom_login_security (
  user_id uuid primary key references auth.users(id) on delete cascade,
  failed_attempts integer not null default 0,
  failure_window_started_at timestamptz,
  locked_until timestamptz,
  current_session_id uuid,
  updated_at timestamptz not null default now()
);

create table private.zoom_admin_events (
  id bigint generated always as identity primary key,
  actor_user_id uuid references auth.users(id) on delete set null,
  target_user_id uuid references auth.users(id) on delete set null,
  event_type text not null,
  metadata jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);
```

- [ ] **Step 2: Add the creator-admin helper in the private schema**

```sql
revoke all on schema private from public;
grant usage on schema private to authenticated;

create or replace function private.zoom_has_valid_access()
returns boolean
language sql
stable
security definer
set search_path = public, private, pg_catalog
as $$
  select exists (
    select 1
    from public.zoom_profiles p
    join private.zoom_login_security s on s.user_id = p.id
    where p.id = auth.uid()
      and p.status = 'active'
      and s.current_session_id is not null
      and s.current_session_id::text = auth.jwt() ->> 'session_id'
  );
$$;

create or replace function private.zoom_is_creator_admin()
returns boolean
language sql
stable
security definer
set search_path = public, private, pg_catalog
as $$
  select private.zoom_has_valid_access()
    and exists (
      select 1
      from public.zoom_profiles p
      where p.id = auth.uid()
        and p.role = 'creator_admin'
        and p.status = 'active'
    );
$$;

revoke all on function private.zoom_has_valid_access() from public;
revoke all on function private.zoom_is_creator_admin() from public;
grant execute on function private.zoom_has_valid_access() to authenticated;
grant execute on function private.zoom_is_creator_admin() to authenticated;
```

- [ ] **Step 3: Enable RLS and add least-privilege policies**

```sql
alter table public.zoom_profiles enable row level security;
alter table public.zoom_agent_slots enable row level security;

create policy "zoom profile self read"
on public.zoom_profiles for select
to authenticated
using ((select auth.uid()) = id and private.zoom_has_valid_access());

create policy "zoom admin reads profiles"
on public.zoom_profiles for select
to authenticated
using (private.zoom_is_creator_admin());

create policy "zoom admin manages slots"
on public.zoom_agent_slots for all
to authenticated
using (private.zoom_is_creator_admin())
with check (private.zoom_is_creator_admin());
```

Private tables remain outside the exposed `public` schema and are accessed only through server-side code or narrowly scoped functions.

### Task 2: Add invite storage and atomic claim reservation

**Files:**
- Create via CLI: run `supabase migration new zoom_invite_claiming`, then edit the exact generated migration path printed by the CLI.
- Test: SQL concurrency/reuse checks.

**Interfaces:**
- Produces `private.zoom_invites`.
- Produces `private.zoom_reserve_invite(initials, code_hash, claim_token)`.
- Produces `private.zoom_finalize_invite(invite_id, claim_token, user_id)`.
- Produces `private.zoom_release_invite(invite_id, claim_token)`.

- [ ] **Step 1: Create invite table**

```sql
create table private.zoom_invites (
  id uuid primary key default gen_random_uuid(),
  slot_id uuid not null references public.zoom_agent_slots(id) on delete cascade,
  code_hash text not null,
  state text not null default 'active' check (state in ('active','claiming','used','revoked')),
  claim_token uuid,
  claim_started_at timestamptz,
  created_by uuid references auth.users(id) on delete set null,
  created_at timestamptz not null default now(),
  used_at timestamptz,
  used_by uuid references auth.users(id) on delete set null,
  revoked_at timestamptz
);

create unique index zoom_one_active_invite_per_slot
on private.zoom_invites(slot_id)
where state in ('active','claiming');
```

- [ ] **Step 2: Implement atomic reserve function**

The function must lock the matching active invite row, compare normalized initials through its slot, set `state='claiming'`, persist `claim_token`, and return only `invite_id` + `slot_id`.

- [ ] **Step 3: Implement finalize/release functions**

`zoom_finalize_invite` must only succeed when `state='claiming'` and `claim_token` matches; set `state='used'`, `used_at=now()`, `used_by=user_id`, and mark the slot `claimed`.

`zoom_release_invite` must revert only the same claim token back to `active` if account creation fails.

- [ ] **Step 4: Verify one-time behavior**

Expected scenarios:
- first reservation succeeds,
- second simultaneous reservation returns no row,
- finalize makes code unusable,
- release restores usability only for matching claim token,
- revoked invite cannot reserve.

### Task 4: Implement username login gateway

**Files:**
- Create: `supabase/functions/login/index.ts`
- Test: integration script `supabase/tests/login-flow.test.ts`

**Interfaces:**
- Consumes `LoginRequest`.
- Produces `LoginSuccess` or generic non-enumerating errors.

- [ ] **Step 1: Write integration tests first**

Cover:
- valid login,
- wrong password,
- unknown username has same public message as wrong password,
- 5 failures inside 10 minutes locks for 15 minutes,
- deactivated user blocked,
- successful login resets failure counters,
- second successful login replaces `current_session_id`.

Public error copy for wrong/unknown credentials must be exactly:

```json
{ "error": "Username or password is incorrect." }
```

- [ ] **Step 2: Implement `login` using current Supabase key model**

Use current Supabase key handling. The function is pre-auth, so deployment uses `verify_jwt=false` and validates the caller as `auth: 'publishable'` with `@supabase/server`. Use `ctx.supabaseAdmin` only for private identity/security lookups. Create a separate publishable-key Supabase client inside the function for `auth.signInWithPassword({ email: internalEmail, password })`; never use the secret/admin client as the end-user session client.

Flow:
1. Normalize username.
2. Query `zoom_profiles` + private identity/security with admin client.
3. If user missing, run a constant-shape response path and return generic error.
4. If `locked_until > now()`, return temporary-lock message.
5. If profile deactivated, return deactivated message.
6. Call Supabase Auth `signInWithPassword` against the hidden internal email.
7. On failure, update failure window/counter and lock at threshold.
8. On success, obtain the JWT `session_id`, persist it as `current_session_id`, reset failed-login fields, append login admin event, and return tokens + safe profile fields.

- [ ] **Step 3: Verify session ID is stored**

Decode/inspect the returned user JWT only after signature-valid Auth issuance; compare its `session_id` to `private.zoom_login_security.current_session_id`.

- [ ] **Step 4: Deploy with `verify_jwt=false` and verify public invocation**

Do not place any secret key in source. Edge Functions read `SUPABASE_SECRET_KEYS` from environment.


### Task 5: Implement account activation

**Files:**
- Create: `supabase/functions/activate-account/index.ts`
- Test: `supabase/tests/activation-flow.test.ts`

**Interfaces:**
- Consumes `ActivateRequest`.
- Produces created profile + immediate login session or activation-success response.

- [ ] **Step 1: Add failing activation cases**

Tests must cover valid activation, wrong initials, wrong code, revoked code, reused code, regenerated code invalidating the previous code, duplicate username, duplicate initials slot, password shorter than 8, and concurrent double redemption.

- [ ] **Step 2: Implement activation state machine**

Flow:
1. Normalize/validate inputs.
2. SHA-256 hash the invite code.
3. Reserve invite atomically with a fresh claim token.
4. Verify requested username is currently free.
5. Create hidden email: `z_<uuid>@auth.zoom.invalid`.
6. Create Auth user with `email_confirm: true` and submitted password.
7. Insert `zoom_profiles`, `zoom_auth_identities`, `zoom_login_security`.
8. Finalize invite claim and slot assignment.
9. If any step after Auth creation fails, delete the newly created Auth user and release the invite reservation.
10. Return a safe activation-success response; never return hidden email. The browser then calls the normal username `login` function with the chosen username/password to obtain the session, so there is only one token-issuance path.

- [ ] **Step 3: Verify double-submit behavior**

Two activation requests using the same invite must produce exactly one Auth user/profile.

- [ ] **Step 4: Deploy and run integration suite**

- [ ] **Step 5: Commit**

